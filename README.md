# 法扣案件公文套版工具

保全法扣作業專用的公文套版工具。選擇情境、填寫案件資料，就能自動產出公文內文、解約金明細表，並列印套印信封。所有資料僅在瀏覽器本機處理，不上傳伺服器。

線上網址：https://mstuiospace.github.io/csv_tools/

## 功能

- **公文內文**：依填寫資料自動組出主旨與說明段落，一鍵複製（貼到 Word／公文系統會保留標楷體 16pt）
- **對內備註**：依日期、給付方式、第三點自動產生，可手動編輯；一旦手改過就不再被自動覆蓋
- **解約金明細表**：自動計算實領金額、金額防呆檢查，可線上預覽與列印
- **信封套印**：完全比照公司信封範本的版面，可微調校正位移後直接套印

# 給接手者的技術筆記

## 專案結構

單一 `index.html`，無建置流程，純前端。除 Google Fonts 外無外部依賴，可離線使用。透過 GitHub Pages 部署。

## 信封套印：最重要的一節，請務必先讀

### 版型座標的唯一正確來源是「範本 PDF」，不是 docx

**不要**從 `小白信封-男女共用版.docx` 的文字方塊錨點去推算位置。docx 存的是相對座標：

```xml
<wp:positionH relativeFrom="column"><wp:posOffset>-451440</wp:posOffset></wp:positionH>
```

它只說「相對於某參考點往左 12.54mm」，而那個參考點在紙上的絕對位置**檔案裡沒有寫**，必須重現 Word 的排版引擎才能得出（段落由右往左的推進量、行高與網格對齊、直書時的邊界旋轉…）。曾經據此推導出整組座標，實測結果：

- 垂直方向整組偏差約 **45mm**（誤把直書上邊界當成 `pgMar right`=20mm，實際應為 `pgMar top`=60mm）
- 水平方向差 1~16mm
- 另一次嘗試「模擬信封置中送紙、把座標左移 38.5mm 同時把紙張設成 120mm 寬」，等於偏移套用兩次，實測整體偏左 38.5mm

**正確做法**：用 Word 把 docx 另存成 PDF，從 PDF 讀座標。PDF 存的是 Word 已經排版完成的絕對座標，是事實而非推導。

### 若日後範本異動，維護步驟

1. 用 Word 開啟新範本 → 另存新檔 → PDF
2. 用 PyMuPDF 解析（本機已安裝，`import fitz`）：

```python
import fitz
d = fitz.open('範本.pdf'); p = d[0]
PT2MM = 25.4/72
for blk in p.get_text('dict')['blocks']:
    for ln in blk.get('lines', []):
        for sp in ln['spans']:
            x0,y0,x1,y1 = [v*PT2MM for v in sp['bbox']]
            print(sp['text'], sp['font'], sp['size'], x0, y0, x1, y1)
```

3. 依中心線分欄（同一直書欄的字，x 中心相近），取每欄的「中心線距紙張右緣」與「文字頂端 y」
4. 更新 `ENV_BASE` 常數
5. 若基準有變動，記得把 `localStorage` 的 key 升版（目前是 `envCalibV3`），讓使用者已存的舊校正值自動失效

**判讀 PDF 數值時的陷阱**：字元的 bbox 不等於文字方塊位置。例如寄件人第三欄量到的頂端比另兩欄高 4mm，但那只是因為該欄首字是橫躺的 Arial 數字、bbox 起算方式與中文不同，方塊本身其實是齊頭的。照抄前要先判斷那個數字代表什麼。

### 目前的版型基準（取自範本 PDF 實測）

紙張 200×270mm。五個直書欄位，以「中心線距紙張右緣」定位：

| 欄 | 內容 | 中心線 | 文字頂端 | 字級 |
|---|---|---|---|---|
| 1 | 郵遞區號 | 56.00 | 68.96 | 22pt（**橫書**） |
| 1 | 地址（同欄下方） | 56.00 | 87.14 | 18pt |
| 2 | 收件人姓名＋稱謂＋收 | 98.20 | 97.72 | 26 / 22 / 24pt |
| 3 | 寄件人單位＋專員 | 145.27 | 135.31 | 12.9pt |
| 4 | 寄件人地址 | 151.81 | 135.31 | 12.9pt |
| 5 | 公文編號＋電話分機 | 158.15 | 135.31 | 12pt |

- 定位方式：`right` 把元素右緣放到中心線，再 `translateX(50%)` 推回，使元素中心落在該線
- `line-height: 1` — PDF 實測 18pt 地址的字距正好等於字級 6.35mm
- 姓名字距 `letter-spacing: 1em` — PDF 實測 26pt 姓名字距 18.38mm，約字級的兩倍
- **郵遞區號必須用橫書**：範本該方塊 `vert=horz`。若誤套直書規則，超過 4 碼會觸發橫躺而往下延伸撞到地址欄

### 直書中的數字排版

規則取自範本 PDF 的字元 bbox 實測，見 `rotateNums()`：

| 情況 | 處理 | 判讀依據 |
|---|---|---|
| 4 碼以內（門牌號等） | `text-combine-upright: all` 壓進一個字寬 | 地址「23」兩字並排、總寬 6.35mm 恰等於 18pt 一個字寬 |
| 超過 4 碼（公文編號、電話、分機） | `text-orientation: sideways` 整串橫躺 | 每個字元 x 固定、y 遞增，寬 5.77mm 等於字高（即旋轉 90°） |

字型：公文編號與電話號碼在範本中是 **Arial**，分機號碼則維持**標楷體**，故 `rotateNums()` 有 `sidewaysFont` 參數。

**不要改用 `transform: rotate()`**：transform 不影響版面配置，旋轉後的文字會覆蓋旁邊內容（需額外用 canvas 量寬度補高度才能避免）。CSS 原生的 `text-orientation` 才是正解。

## 非解約給付：主旨的組句規則

主旨的寫法不是自由發揮，是照實務慣例決定的，改動前請先確認：

| 情況 | 輸出 |
|---|---|
| 全部匯款 | `有關債務人○○○之【類型】債權，本公司已於【日期】匯款新臺幣【各筆金額】元至【對象】指定帳號【手續費】，請查照。` |
| 全部支票 | `隨函檢附債務人○○○之【類型】債權支票影本【張數】【手續費】，請查照。` |
| 匯款與支票並存 | 以「有關…」起首，兩段以「，並」相接 |

- **收款對象**（`ntPayeeText`）：債權人名稱全部填了就列名稱（如「國泰世華銀行」）；否則用人數，**但兩人以內不寫數字**，直接寫「債權人指定帳號」，三人以上才寫「三債權人」
- **給付類型**：可複選，以「及」相接。第五項「已得請領保險金」是多種債權並存時的統稱，第六項「自填」供例外情形
- **張數量詞**：單張寫「乙紙」（公文慣例），多張才用數字
- **手續費 250 元跟著債務人**，不是跟著債權人，所以同一件只扣一次。給付金額不足以扣手續費時，勾選「不扣手續費」會把「（已扣除手續費250元）」整段拿掉
- **說明第三點會自動遞補編號**：若沒有選第二點，第三點的內容會排成「二、」。這是刻意的，公文編號必須連續

## 設計決策與理由

- **對內備註**：自動產生，但使用者一旦手動編輯過（`internalNoteManuallyEdited` 旗標）就停止自動覆蓋
- **明細表註記**：只有一則時顯示「註：」不編號 —— 單獨一個「註1」會讓人誤以為漏寫了後續項目
- **金額防呆採提示而非阻擋**：公文金額情況多，硬性擋掉會卡住作業；且輸入過程中金額本來就會短暫不完整
- **手續費預設 250 且每張保單都扣**：約 95% 案件需扣，欄位可手動改，刻意不加提示以免變成常態性干擾
- **已移除「產出 Word 檔」**：需從 CDN 載入 docx.js，與「離線可用」的定位衝突且經常失敗
- **已移除信封預覽**：與實際列印有落差，改以瀏覽器的列印預覽為準
- **複製公文必須用 `<p>` 分段**：Word 會忽略單一區塊內的 `<br>`，導致全部擠成一段

## 開發／測試注意事項

- **瀏覽器會恢復表單狀態**：重新整理時 `<select>` 會跑回上次的選擇，蓋掉 HTML 的 `selected`。第三點的預設值因此改在初始化時用 JS 明確指定。測試時若「改了沒生效」，先確認是不是這個
- **列印字級比畫面大**（11pt vs 11px），欄寬在畫面上正常不代表列印正常。測試表格排版要模擬實際 A4 尺寸與列印 CSS
- **列印視窗會被瀏覽器封鎖**（尤其 `file://`），已加提示訊息，不再無聲失敗
- **版本號需手動維護**：`APP_VERSION` 與 `APP_UPDATED` 兩個常數，改版時記得同步更新，否則首頁與「關於」顯示的日期不會變
- 範本 docx／PDF 與座標分析暫存檔都在 `.gitignore` 中，不上傳公開 repo（含公司資訊）
